# Decisions

Choices made where the prompt was silent or where the environment forced a trade-off. Newest first.

| D61 | **Account deletion (DPDP Act 2023) is anonymisation, not hard delete; exports are self-serve asynchronous jobs** (M5.12). Deletion anonymises: name "Deleted user", email/mobile/password/googleId/2FA null, status DELETED + deletedAt; sessions, device tokens, notifications, OTP codes, matching leads deleted. Profile/business PII null, business soft-deleted; formData {}, customer messages/tickets "[deleted]", booking notes and review text null, reminders cancelled, open exports rejected. Customer uploaded files: bytes deleted after commit, row kept with deletedAt (download 410). Untouched (GST/legal retention): invoices, payments (rawWebhook included), refunds, credit notes, certificates, orders, applications rows, staff deliverables, audit log (no PII written to audit). Export created without approval by queue job; ZIP kept 7 days, downloaded via 5-min signed link (scope data-exports, D50 pattern) with hourly cleanup. Deletion requires staff approval (privacy.manage); blockers (in-progress applications, partially paid orders, upcoming bookings) return 409. Re-check: password or ACCOUNT_DELETION OTP; staff/consultant accounts cannot be deleted here (403). | Complies with DPDP Act 2023 right to erasure while preserving mandatory GST and tax retention records (CGST Act s.36). Hard delete would break foreign keys on invoices/payments/certificates or force orphan records. Retaining stub rows with deletedAt and removing bytes/PII satisfies privacy requirements without corrupting audit trails or accounting books. Background queue for exports protects request thread and isolates CPU/memory intensive archiving. |
| D59 | **Notifications are sent by a `notifications` queue job per notification × channel, recorded in a `NotificationDelivery` row** (M6.3). Listeners and the reminder job call `NotificationQueueService.enqueue({ …, sourceKey, templateId, sendAt? })`: it inserts the row (status QUEUED, title/body/link/variables in `content`) with a **unique `idempotencyKey` = event \| sourceKey \| user \| channel** — `sourceKey` names the occurrence (payment, invoice, refund, document version, message, ticket (+ resolvedAt), stage-history row, certificate, reminder + offset), so a replayed webhook or re-emitted event inserts nothing and sends nothing — then adds a job with **job id = row id** (`delay` from `sendAt`, for M8.9 reminders). The worker claims the try (conditional `attempts` increment), sends through `NotificationDispatcherService` (preferences unchanged) and records: SENT (+ provider message id), DELIVERED for in-app, **SKIPPED** (opted out, no device — a 5th status beyond the four asked for) or, on error, `lastError` with emails/numbers masked. Temporary errors retry 6 tries, 30 s × 4ⁿ capped at 1 h (+≤10 % jitter), then FAILED and dead-lettered; **permanent** ones (no address/number, no DLT id, template error, provider 4xx except 408/429, MSG91 `type: error`) are FAILED after one try. Staff with the new **`notifications.view`** (ADMIN by default) see `GET /api/admin/notifications/deliveries` (status, channel, event, user, date; no content, no address) and `POST …/{id}/retry` (FAILED only, else 409; audited `notification.retry`; full tries again). Provider reports `POST /api/notifications/callbacks/msg91?token=` (shared token, MSG91 doesn't sign) and `…/sendgrid` (ECDSA signature over timestamp + raw body) move **only SENT** rows to DELIVERED / FAILED; with no secret configured the route is 404 and SENT is final (SMTP, FCM, WhatsApp stub). OTPs still go straight through the channels, in the request. On start, QUEUED rows untouched for 15 min (last 7 days) are queued again. | The send no longer runs inside the request that emitted the event, so a slow or failing provider never slows a status change and a failure is retried instead of lost. The row is written before the job, so Redis being down loses nothing (boot sweep), and the unique key — not a read-then-write check — makes duplicates impossible even under concurrent emits. Keeping content on the row lets staff retry days later; keeping it out of the admin API keeps PII out of the log screen. A natural `sourceKey` instead of the event's random id is what makes a *re-emitted* event (a new id) a duplicate. OTPs stay synchronous because the user is waiting and the caller must know it failed. Delivery is at-least-once: a crash between the provider accepting and the row update can send twice. |
| D58 | **Booking holds are enforced by the database, and paid through the existing payment flow** (M8.8). `POST /api/bookings { consultantSlug, type, startAt }` takes the consultant row lock (`SELECT … FOR UPDATE`), moves overlapping holds that ran out to the new status **EXPIRED**, checks `startAt` is one of the slots `generateSlots` offers right now (busy = CONFIRMED + PENDING_PAYMENT with `holdExpiresAt > now`), and inserts a PENDING_PAYMENT booking with `holdExpiresAt = now + 10 min`, fee from the consultant, code `BKG-<IST year>-<6 digits>` (sequence `booking_code_seq`). Backstop: exclusion constraint `Booking_no_overlap` (btree_gist, `consultantId =`, `tsrange(startAt,endAt) &&`, only for PENDING_PAYMENT / CONFIRMED) — a predicate can't use `now()`, which is why stale holds are set EXPIRED before the slot is reused. A customer has at most one live hold (a new one releases the old); clicking the same slot again returns the same booking; a 1-minute cron tidies expired holds. Payment: `POST /api/bookings/{id}/payment` reuses one open `Payment` (with `bookingId`) for the fee while the hold lasts and attaches the gateway order with `CheckoutService.attachGatewayOrder` (same compare-and-set as D43); `…/payment/callback` only sets PENDING (D45). The webhook (D44, same event claim + transaction) sends a booking's payment to `BookingPaymentsService.applyWebhook` under the consultant lock: captured → booking CONFIRMED, audit `booking.payment_received`, event `booking.confirmed`. Paid after the hold ran out → still confirmed if the slot is free, else outcome **`slot_taken`** (payment SUCCESS kept for a refund, booking EXPIRED, logged as needing attention, like `order_not_pending`); paid for an already confirmed/closed booking → `booking_not_pending`. No `payment.succeeded` for bookings (its listeners need an order). Dev only: `POST /api/payments/mock/{paymentId}/pay` (404 unless the mock gateway is in use; caller's own open payment) plays the gateway — captures and delivers the signed webhook through the real code — so the flow can be completed in a browser. | The lock gives clear 409s; the constraint makes a double booking impossible even if some future code path forgets the lock. Reusing the application payment rules keeps one idempotency story for refunds and reconciliation. |
| D57 | **Availability is weekly windows + date exceptions, turned into slots by one pure function** (M8.6). `AvailabilitySlot` rows are either a weekly window (`weekday`, never blocked) or a date exception on an IST calendar date (`date` is now `@db.Date`): blocked hours (`isBlocked`; no times = whole day `00:00–24:00`) or extra hours. CHECK constraints keep exactly one of weekday/date and valid `HH:MM` times (`24:00` = end of day, end after start). `generateSlots(rules, { from, to, now, busy })` (`packages/types/src/availability.ts`) works in fixed IST (UTC+05:30, no DST): per date it merges the weekday's windows with that date's extra hours, lays sessions every `sessionMinutes + bufferMinutes` from each window's start, drops a session that would cross the window's end, one that overlaps blocked hours (blocked beats weekly and extra), one starting before `now + minNoticeMinutes`, and one within `bufferMinutes` of a busy interval. New consultant columns `bufferMinutes` (0) and `minNoticeMinutes` (120). The consultant edits their own schedule at `/api/consultants/me/availability` (`admin.access`, so 2FA like the portal, plus an APPROVED consultant profile, else 403; `PUT` replaces the weekly windows + settings in one transaction; exceptions are `POST`/`DELETE …/exceptions`; all audited). `GET /api/public/consultants/{slug}/slots?from&to` (IST dates, default the next 7 days, at most 14) answers for APPROVED consultants only. | One tested function decides what is bookable, so the slots page, the booking hold (M8.8) and later the directory's "available today" can't disagree. A date column avoids the IST-midnight off-by-one of storing dates as instants. |
| D53 | **Refunds and credit notes** (M4.13). `POST /api/admin/payments/{id}/refunds` (`payments.view` + `payments.refund`; ADMIN only by default — Support/Operations get 403) with a required **`Idempotency-Key` header**, stored on the `Refund` (unique per payment): a retry with the same key returns the first refund (409 if amount/reason differ) and never calls the gateway again. Only a SUCCESS or PARTIALLY_REFUNDED payment can be refunded (409 otherwise, including while a refund is in flight — one refund at a time per payment), at least ₹1 and at most the amount minus every refund not FAILED (400). The check, the `Refund` (INITIATED), payment → REFUND_INITIATED and the audit row are written **in one transaction under the payment's row lock**; the gateway is called after the commit with our refund id as `receipt` and `notes.refund_id`. A refusal (non-retryable gateway error) marks it FAILED at once → 502; a timeout leaves it INITIATED for the webhook. `refund.processed` / `refund.failed` webhooks go through the existing event-row claim (D44), are matched by gateway refund id or, if the webhook beat us, by our id in the notes, and the payment status is always **worked out again from all its refunds** (`paymentStatusAfterRefunds`), so a failure puts it back exactly where it was. **Credit notes** are numbered `CN/<FY as 2627>/<6 digits>` (e.g. `CN/2627/000001`, 14 characters) from their own gap-free counter per financial year (`CreditNoteSequence`, same SQL as D47), issued on `refund.processed` in their own transaction under the order lock with a 10-minute sweep (as D48), and copy seller, buyer, place of supply and tax split from the refunded payment's invoice. Lines: a refund of everything not yet credited takes exactly what is left of every invoice line; a smaller one takes the **professional fee + GST first** (a proportional share of each service line) and **government fees only with what remains** — owner's decision, 17-Oct-2026 — GST worked back out at the line's rate and CGST/SGST kept within a paisa (`creditNoteLines`). The PDF is the invoice template titled "Credit Note" with the original invoice number/date and the reason; downloads as D50 (`/api/credit-notes/{id}/link`). | One row lock makes "check refundable, then insert" safe against parallel clicks; holding no lock during the network call keeps the webhook from waiting on it. Never retrying a timed-out refund blindly avoids a double refund (Razorpay may have made it). Deriving the status from the refund rows means no stored "previous status" can go stale. A separate `CN` series is what GST rule 53 expects (credit notes are their own consecutive series); copying from the invoice keeps the credit note consistent with it even if Settings change. Fee first (the reverse of D48's advance, which collects government fees first) because government fees are usually already paid out to the government by the time a refund is asked for. A seller `invoicePrefix` of `CN` would look like credit notes — not blocked yet. |

| D48 | **One invoice per payment the webhook applied, issued by a `payment.succeeded` listener in its own transaction, with a 10-minute sweep as the backstop** (M3.21). An advance and its balance each get an invoice: a payment of everything not yet invoiced takes exactly what is left of every line; a smaller one (the advance) takes the **government fees first**, then a share of each line's fee + GST, with the GST worked back out at the line's rate (`invoiceLines`). **Seller, buyer, place of supply and lines are copied onto the invoice** (`seller`/`buyer`/`lines` JSON); a balance invoice keeps the first invoice's CGST+SGST/IGST split. | D47 | **Invoice numbers are `<prefix>/<FY as 2627>/<6 digits>`, e.g. `BN/2627/000123`, from a counter row per financial year** (M3.20). The prefix is now **at most 4 characters** (was 6). The counter (`InvoiceSequence`) is bumped with `INSERT … ON CONFLICT DO UPDATE … RETURNING` **inside the transaction that creates the invoice**; the year is the invoice date's FY in IST (1 April – 31 March). | GST rule 46 allows at most 16 characters: the spec's `BN/2026-27/000123` is 17, and a 6-character prefix would leave room for only 4 digits. 4 + 1 + 4 + 1 + 6 = 16 covers 999,999 invoices a year. A Postgres sequence (as for order codes, D35) skips numbers on rollback; the row lock makes concurrent invoices of the same year queue up and a rollback hands the number back, so the series is gap-free. Invoices are a few a minute at most, so serialising them costs nothing. |
| D46 | **Part payment is one advance, then the balance** (M3.19). The advance is **each line's government fee in full plus the package's advance % of the fee after discount + GST, rounded up to whole rupees** (`advancePayment`); the balance is the rest. The % is **copied onto `OrderItem.advancePercent`** with the prices while the order is a draft, so it is frozen once payment starts. The customer picks a **plan** (`FULL` / `ADVANCE` / `BALANCE`), never an amount; an open payment is reused only when it is for the same amount, so switching plans makes one payment per amount. **The advance does everything a full payment does** (order PARTIALLY_PAID, application submitted, coupon redeemed); the balance only moves the order to PAID. Money beyond the total is recorded but not applied (`overpaid`). | Government fees are paid out early, at filing, so an advance that didn't cover them would leave the firm funding them; rounding to rupees keeps the numbers readable and never under-collects. Freezing the % follows D40 (amounts fixed once payment starts). Plans keep the "client sends no amounts" rule from D40/D43. Submitting on the advance is the point of paying in part — work starts — and keeps one path for coupons and history. |
| D45 | **The browser never decides a payment's result** (M3.18): Checkout's success callback (`POST /api/applications/{id}/payment/callback`) only moves a payment whose signature verifies from CREATED to **PENDING** ("confirming"), and the payment page reads **`GET /api/applications/{id}/payment`**, whose `outcome` comes from `paymentOutcome(order status, latest payment status)` — PAID only once the webhook has paid the order. The page **polls** (2 s, then 5 s, for 2 minutes) instead of a push channel, and keeps `?confirming=1` in the URL so a reload still waits rather than showing an earlier failed attempt. Success, confirming and failure are **one page** (`/apply/{service}/{id}/payment`) choosing its view from the outcome. | PROMPT §7.5 says never trust the client callback; making it unable to pay anything means closing the browser loses nothing (the webhook does the work) and a forged callback can at most show "confirming". PENDING is the spec's CREATED → PENDING step and lets payments where checkout finished be told apart from abandoned ones. Polling is simple, works behind any proxy and needs no new infrastructure for a wait of seconds; one page keyed by outcome shows the right thing whenever the customer comes back. |

A capture of a payment we marked FAILED still pays the order | Claiming the event id inside the applying transaction means a redelivery that arrives while the first is still running waits on the unique index and then does nothing, and a failed attempt rolls the claim back so the gateway's retry works. The payment-status check covers the same payment under a new event id. A non-2xx answer makes Razorpay retry for 24 h, which cannot fix a mismatch, so those need a person, not a retry. Refusing the order after the money is taken would be worse for the customer than one extra use of a coupon. Razorpay lets the customer retry inside the same checkout, so a failed attempt is not final for its order. |
