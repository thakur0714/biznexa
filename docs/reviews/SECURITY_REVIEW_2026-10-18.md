# Security review — 18-Oct-2026 (M12.1, M12.2)

**Scope:** `apps/api` in full; `apps/web` and `apps/admin` where they touch auth, redirects and headers; `packages/types` form schemas; the dependency tree (`pnpm audit`). Reviewed against `origin/main` at `a115e2b`, branch `claude-m12.1`.
**Not repeated here:** customer/staff data isolation (IDOR) — covered by M5.13 (`test/data-isolation.e2e-spec.ts`) and the route × role sweep in M12.4.
**Decisions:** D64 (rate limits, CSRF, headers, CORS) and D65 (sensitive data) in `docs/DECISIONS.md`.

## Findings

| # | Finding | Severity | Status | Fix / test |
|---|---------|----------|--------|------------|
| S1 | **Password reset token could be replayed.** The token from `POST /auth/otp/verify` (purpose `RESET_PASSWORD`) was a plain 10-minute JWT. Its comment said it was one-time, but nothing enforced that. Anyone holding it, for example from browser history or a shared device, could set the password again for 10 minutes after the real reset. | High | Fixed | The token now carries a fingerprint of the password hash it replaces. `resetPassword` checks the fingerprint and updates only `WHERE passwordHash = <old>`, so a used token or one issued before another change is refused. `token.service.ts`, `auth.service.ts`. Test: `security.e2e-spec.ts` › *password reset tokens work once*. |
| S2 | **Account pre-hijacking through Google sign-in.** An attacker could register with a victim's email, which is never verified, and keep a session. When the victim later used "Sign in with Google", the account was linked and marked verified, but the attacker's password and sessions still worked. | High | Fixed | When Google links to an account whose email was **unverified**, the password is cleared, every refresh token is revoked and the event is audited (`user.google_link_unverified`). A verified account just links. Tests: `security.e2e-spec.ts` › *Google sign-in on an existing account* (both cases). |
| S3 | **The same pre-hijack worked through OTP login** on a mobile number or email that the account never verified. | Medium | Fixed | An OTP `LOGIN` on an unverified channel takes the account over in the same way: the password is cleared, sessions are revoked and the event is audited (`user.otp_login_unverified`). The normal `VERIFY_MOBILE` step after registering is unchanged. Tests: `security.e2e-spec.ts` › *OTP login with a mobile the account never verified*. |
| S4 | **Sensitive routes had no limit of their own.** `POST /auth/password/change` had none, so someone holding a stolen access token could brute-force the current password at 120 requests a minute. `POST /auth/refresh`, both application payment routes (create and callback), both booking payment routes and the mock pay route also relied only on the global limit, which let anyone spam gateway order creation. | Medium | Fixed | `src/common/rate-limits.ts` holds named per-IP limits: `AUTH_LIMIT` 10/min, `OTP_LIMIT` 5, `REFRESH_LIMIT` 30, `PAYMENT_LIMIT` 10, `UPLOAD_LIMIT` 30. They are applied to every route in the matrix below. Test: `rate-limits.e2e-spec.ts` checks every sensitive handler declares a limit of 60/min or less, then turns the throttler on (`THROTTLE_IN_TESTS=1`) and gets a 429 with `Retry-After` on the 11th login. |
| S5 | **PAN and bank account numbers stored in plain text in `Application.formData`.** Business PAN, director, nominee and signatory PANs, and account numbers were stored as plain JSON. Every staff member who could open the application, consultants included, saw them in full. (`BusinessEntity.pan` and staff 2FA secrets were already encrypted.) | Medium | Fixed | `sensitive-form-data.ts`. Answers whose field uses the PAN or bank-account format are stored as `{ "$enc": "v1.…" }` (AES-256-GCM, the existing `encryptField`), including inside repeater rows. When reading: the owning customer and the data export get the full value, staff with `applications.update` (Admin, Operations) get it in full, and anyone else (Consultant) gets it masked (`ABCDE****F`, `••••9012`). Tests: `sensitive-form-data.spec.ts`; `application-form.e2e-spec.ts` (the database row holds no plain PAN; the customer and an admin see it, an assigned consultant sees it masked). |
| S6 | **Personal data in logs.** `PrismaExceptionFilter` logs Prisma error messages, which quote the values involved. For OTPs, `SmsChannel` logs `user=<mobile>` because the OTP's `userId` is the target. Notification and event errors include whatever their messages contain. | Medium | Fixed | `RedactingLogger` (`src/common/redacting-logger.ts`) is installed as the app logger in `main.ts`. Before writing, it scrubs emails, Indian mobile numbers, PANs, Aadhaar-shaped numbers, JWTs, bearer tokens and `password=`/`otp:`/`token=` pairs from messages, contexts and stack traces, and replaces values under sensitive keys in logged objects. Writing the tests showed that Nest treats a trailing string argument as the log *context*, so contexts are scrubbed too. Test: `redacting-logger.spec.ts` (13 cases, including actual stdout/stderr output). |
| S7 | **Admins could add Aadhaar number fields** to a service form through the form builder. The ready-made forms never ask for one; the existing test only covered those. | Low | Fixed | `formSchema` refuses a field (or repeater sub-field) whose name mentions Aadhaar/UIDAI, or whose label asks for the number ("Aadhaar number", "Aadhar No.", "UID number"). Labels that only mention Aadhaar ("Full name (as on Aadhaar)") are still allowed. Test: `form-schema.test.ts` › *Aadhaar numbers (M12.2)*. |
| S8 | **HSTS was not set up deliberately.** Helmet's default HSTS was sent in every environment (pointless on http://localhost). The web and admin apps sent no HSTS at all. | Low | Fixed | API: `helmetOptions()` sends HSTS (2 years, includeSubDomains) and the default CSP in production only. Web/admin: `Strict-Transport-Security` in production only. Tests: `security.spec.ts`, `security.e2e-spec.ts` (headers present, no `X-Powered-By`), `next-config.test.ts` in web and admin. |
| S9 | **`CORS_ORIGINS` was not validated.** A `*`, a path or plain http in production would have been accepted silently. (`cors` with an array never matches `*`, so this was a misconfiguration risk, not an open hole.) | Low | Fixed | `env.ts` refuses wildcards, non-origins and empty lists, and requires https in production, so the API does not start with a bad list. Tests: `security.spec.ts` › *CORS allow-list*; `security.e2e-spec.ts` (an allowed origin gets `Access-Control-Allow-Origin` + credentials, an unknown one gets nothing). |
| S10 | **CSRF defence relied on SameSite alone.** The refresh cookie is httpOnly, `SameSite=Lax` and scoped to `/api/auth`, and every other route takes a bearer token, so cross-site forms can't use it today. | Low | Hardened | `refreshCookieOriginCheck` on `/api/auth` refuses a non-GET request that carries `bn_rt` with an `Origin` outside the allow-list (403). Requests with no Origin (the Next.js server-side rewrite, curl) are unaffected. Tests: `security.spec.ts`, `security.e2e-spec.ts` › *refuses the refresh cookie from an unknown origin*. |
| S11 | **Dependency audit:** 46 advisories (3 critical, 29 high). **None are in the API's runtime dependencies.** All are in development or build tools: Expo CLI (`tar`, `@xmldom/xmldom`, `node-forge`), Metro (`image-size`, `postcss`), the Prisma CLI (`deepmerge-ts`, `mysql2`), Vitest (`tinypool`) and ESLint (`braces`). | Info | Partly fixed | Added pnpm overrides for `postcss` (^8.5.18) and `mysql2` (^3.22.0), which are semver-compatible. The rest need major version bumps of the Expo/Vitest toolchains or have no patch yet: accepted, see D64 and A1. 40 advisories remain, all dev-only. |

## Checked, no issue found

- **Injection:** every `$queryRaw`/`$executeRaw` is a tagged template or uses `Prisma.join`, so values are parameterised. There is no `$queryRawUnsafe`, string-built SQL or shell execution. CSV exports (applications, reports, certificate import errors) escape formula characters (D53).
- **Authentication and sessions:** access tokens are HS256 with issuer checked. The guard refuses any token whose `typ` is not `access`, so a reset token can't be used as a session. Refresh tokens are stored hashed, rotated, and reusing one revokes its whole family. Logout revokes the presented token; logout-all, password change and reset revoke the others. A 2FA-pending staff token carries no permissions. TOTP codes are single-use (atomic last-step update) with a 15-minute lock after 5 failures. Setup is refused once 2FA is enabled. Staff password resets and OTP logins still start a 2FA-pending session.
- **SSRF:** the API calls only fixed provider hosts (Razorpay, MSG91, SendGrid, FCM, Turnstile) and the clamd host from env. The PDF renderer blocks all network requests (`pdf-renderer.spec.ts`). Nothing fetches a URL that a user supplies.
- **File upload:** extension allow-list, then first bytes checked against the type while streaming, a size cap, virus scan before any download, random keys outside any public folder, and downloads only through scoped, timing-safe signed links with `nosniff` and a sandbox CSP. Media images are re-encoded by sharp.
- **Open redirects:** web and admin `?next=` go through `safeRedirectPath` (URL-parsed, same origin only). The admin also refuses loops to `/login` and `/two-factor`. The API never redirects.
- **Mass assignment:** every body goes through a zod object, which drops unknown keys. No service spreads request input into user, role or permission writes. `PATCH /auth/me` accepts only name and email; changing the email resets `emailVerified`.
- **Signed links (invoices, credit notes, data exports, report exports, files):** the HMAC covers scope + id + expiry + disposition, so a link for one kind of record can't open another.
